2วัตถุประสงค์และความต้องการของระบบ Objectives & Requirements

2.1 วัตถุประสงค์หลักของโครงงาน (Project Objectives)

  1. การแบ่งแยกสิทธิ์และโซนเครือข่าย (Network Segmentation): เพื่อป้องกันไม่ให้ผู้ไม่หวังดีสามารถเจาะเข้าถึงฐานข้อมูลที่มีความสำคัญสูงได้โดยตรง หากเกิดช่องโหว่ที่ชั้นเว็บเซิร์ฟเวอร์
  2. การปฏิบัติตามหลักสิทธิ์น้อยที่สุด (Principle of Least Privilege): กำหนดสิทธิ์ของทั้งผู้ใช้งาน, เครื่องเซิร์ฟเวอร์ (IAM Instance Roles), และกฎไฟร์วอลล์ (Security Groups) ให้มีสิทธิ์เท่าที่จำเป็นต้องใช้เท่านั้น
  3. การเข้าถึงเครื่องอย่างปลอดภัยโดยไม่เปิดพอร์ต 22 (Zero Public SSH via AWS SSM): ยกเลิกการเปิดพอร์ต SSH สู่สาธารณะ และยกเลิกการใช้ Bastion Host เพื่อขจัดความเสี่ยงจากการถูกโจมตีแบบ Brute-Force
  4. การปกป้องข้อมูลและการเข้ารหัสทั้งระบบ (End-to-End Cryptography): เข้ารหัสข้อมูลทั้ง In-Transit (TLS 1.3) และ At-Rest (AWS KMS AES-256) พร้อมบริหารความลับผ่าน AWS Secrets Manager
  5. ความพร้อมใช้งานสูงและการขยายตัวอัตโนมัติ (High Availability & Elasticity): กระจายเวิร์กโหลดข้าม AZ และใช้ Auto Scaling Group เพื่อรองรับการทายผลช่วงบิ๊กแมตช์

2.2 ความต้องการด้านความปลอดภัย (Security Requirements)

รหัส ข้อกำหนดด้านความปลอดภัย แนวทางและกลไกที่นำมาแก้ปัญหา (Implementation)
SEC-01 Database Isolation ฐานข้อมูล RDS ถูกวางใน Isolated Subnet ที่ไม่มี Route 0.0.0.0/0 และกำหนด Publicly Accessible = No
SEC-02 Traffic Inspection ติดตั้ง AWS WAF เชื่อมต่อหน้า Application Load Balancer บังคับใช้ Managed Rules (SQLi, XSS, Bad Inputs) และ Rate Limiting
SEC-03 In-Transit Encryption ALB บังคับใช้ SSL/TLS Certificate จาก AWS ACM พร้อม Redirect HTTP พอร์ต 80 สู่ HTTPS พอร์ต 443 ด้วยรหัส 301
SEC-04 At-Rest Encryption EBS Volumes และ RDS Database ถูกเข้ารหัสด้วย AWS KMS CMK (Key: aws/rds และ aws/ebs) อัลกอริทึม AES-256
SEC-05 Zero Bastion SSH ไม่เปิดพอร์ต 22 ใน Security Group ใดๆ ผู้ดูแลระบบเข้าถึงเครื่องผ่าน AWS Systems Manager (SSM) Session Manager
SEC-06 Data Integrity (Race Condition) แอปพลิเคชันใช้ ACID Mutex Lock (จำลอง SELECT ... FOR UPDATE) ป้องกัน Double Spending ขณะตัดแต้มทายผล

3หลักการแนวคิด และการดำเนินการตามแนวคิด Design Principles vs Implementation

ในหัวข้อนี้จะอธิบายรายละเอียดว่าระบบยึดถือ หลักการแนวคิด (Security & Architectural Concepts) ใดบ้าง และทางกลุ่มได้ ดำเนินการปฏิบัติจริงอย่างไรกับแนวคิดนั้น (How Implemented on AWS & App) เพื่อให้เกิดความชัดเจนตามเกณฑ์ประเมินโครงงาน:

1

การป้องกันความปลอดภัยเชิงลึก (Defense-in-Depth)

หลักการแนวคิด
ความปลอดภัยไม่สามารถพึ่งพากลไกป้องกันเพียงจุดเดียว (Single Layer of Defense) ได้ หากปราการด่านหน้าถูกเจาะหรือตั้งค่าผิดพลาด ปราการด่านถัดไปต้องสามารถสกัดกั้นการโจมตีได้ทันที
การดำเนินการจริง
  • Edge Tier: กรองคำขอที่ AWS WAF (L7) และ AWS Shield Standard (L3/L4)
  • Network Tier: กรองด้วย Chained Security Groups และ Subnet NACLs
  • Host Tier: ติดตั้ง Nginx Reverse Proxy ซ่อน IP จริง และเปิดใช้งาน IMDSv2
  • Application Tier: ตรวจสอบ JWT Token, RBAC, และ Input Sanitization
  • Data Tier: RDS ใน Isolated Subnet เข้ารหัสด้วย AWS KMS
หลักฐานการตรวจสอบ: S07 Security Groups S15 ALB Listeners S16 WAF Web ACL
2

การให้สิทธิ์น้อยที่สุด (Principle of Least Privilege) & Zero Trust

หลักการแนวคิด
ทุก Entity (ผู้ใช้, เครื่องเซิร์ฟเวอร์, ฐานข้อมูล) จะได้รับสิทธิ์เท่าที่จำเป็นต่อการปฏิบัติหน้าที่เท่านั้น และ "ไม่เชื่อถือใครโดยปริยายแม้จะอยู่ในเครือข่ายเดียวกัน" (Zero Trust)
การดำเนินการจริง
  • EC2 ใช้ IAM Instance Profile ที่แนบเฉพาะ AmazonSSMManagedInstanceCore และ CloudWatchAgentServerPolicy
  • ไม่มีการฝัง AWS Access Key / Secret Key ในโค้ดหรือบน Server โดยเด็ดขาด
  • Security Groups ยอมรับทราฟฟิกเฉพาะ Security Group ID ของชั้นก่อนหน้า (ไม่ระบุ IP กว้าง)
  • ฐานข้อมูล sg-db รับเฉพาะ sg-app บนพอร์ต 5432 และ Deny Outbound 100%
หลักฐานการตรวจสอบ: S08 IAM Role S09 Secrets Manager S07 Security Groups
3

การยกเลิกการเปิดพอร์ต SSH สู่สาธารณะ (Zero Public SSH via AWS SSM)

หลักการแนวคิด
พอร์ต 22 (SSH) เป็นเป้าหมายอันดับหนึ่งของการโจมตีแบบ Brute-force และการสแกนหาช่องโหว่ การเปิด Bastion Host ทำให้เกิดจุดอ่อน (Single Point of Compromise) บน Public Subnet
การดำเนินการจริง
  • ปิด TCP พอร์ต 22 ในทุก Security Group และไม่สร้าง EC2 Key Pair
  • เชื่อมต่อบริหารจัดการเซิร์ฟเวอร์ผ่าน AWS Systems Manager (SSM) Session Manager
  • การเข้าถึงยืนยันตัวตนผ่าน AWS IAM + Multi-Factor Authentication (MFA)
  • คำสั่งที่พิมพ์ผ่านเทอร์มินัลทั้งหมดถูกบันทึกลงใน AWS CloudWatch Logs / S3 โดยไม่สามารถลบประวัติได้
หลักฐานการตรวจสอบ: S01 Root MFA S07 Zero Port 22 S20 SSM Session Manager
4

การปกป้องข้อมูลและการเข้ารหัส (Data Protection In-Transit & At-Rest)

หลักการแนวคิด
ข้อมูลสำคัญ เช่น รหัสผ่าน, ข้อมูลกระเป๋าเงิน, สถิติการทายผล ต้องได้รับการคุ้มครองไม่ให้ถูกดักจับ (Sniffing) หรือถูกขโมยจากดิสก์ (Disk Theft) ได้
การดำเนินการจริง
  • In-Transit: ใช้ TLS 1.3 ผ่าน AWS ACM ร่วมกับนโยบาย ELBSecurityPolicy-TLS13-1-2-2021-06
  • At-Rest: Amazon RDS และ EBS ถูกเข้ารหัสด้วย AWS KMS (AES-256)
  • รหัสผ่าน Master Database และ JWT Secret ถูกเก็บและหมุนเวียนใน AWS Secrets Manager
  • รหัสผ่านผู้ใช้ผ่านการ Hash ด้วยอัลกอริทึมที่ปลอดภัยก่อนจัดเก็บ
หลักฐานการตรวจสอบ: S09 Secrets Manager S10 RDS Encryption S14 ACM Issued

8การเฝ้าระวัง การสำรองข้อมูล และการกู้คืน Monitoring & DR

8.1 การเฝ้าระวังและการบันทึก Log (Monitoring & Observability)

  • AWS CloudTrail (apex-mgmt-trail): บันทึกทุก API Call ระดับ Management Plane เปิดใช้งาน Log File Integrity Validation เพื่อป้องกันการปลอมแปลงบันทึกประวัติ
  • Amazon GuardDuty: ระบบตรวจจับภัยคุกคามอัจฉริยะ วิเคราะห์ VPC Flow Logs, DNS Logs และ CloudTrail Events เพื่อตรวจจับพฤติกรรมผิดปกติ เช่น การขุดคริปโต หรือ Reconnaissance
  • Amazon CloudWatch Alarms: ติดตั้ง 4 Alarms สำคัญ ได้แก่: 1) CPU Utilization > 75% บน App ASG, 2) Unhealthy Host Count > 0 บน ALB, 3) HTTP 5XX Rate > 1% บน ALB, และ 4) Free Storage Space < 2 GB บน RDS ทั้งหมดส่งแจ้งเตือนผ่าน Amazon SNS (apex-security-alerts) ไปยังอีเมลทีมวิศวกร

8.2 แผนการสำรองข้อมูลและการกู้คืน (Backup & Disaster Recovery)

  • Amazon RDS Multi-AZ & Automated Backup: ข้อมูลถูกทำสำเนาแบบ Synchronous ข้ามไปยัง Availability Zone สำรอง (AZ-b) แบบ Real-time พร้อมเปิดระบบ Automated Backup ย้อนหลัง 7 วัน รองรับ Point-in-Time Recovery (PITR) ระดับวินาที
  • EC2 Golden AMI Snapshot: เครื่องเซิร์ฟเวอร์ที่ติดตั้งซอฟต์แวร์และ Hardening เสร็จสมบูรณ์ถูกจัดทำเป็น Golden AMI (apex-web-golden-ami-v1) เพื่อให้ Auto Scaling Group สามารถสปินอัปเครื่องทดแทนได้ทันที
